# DDR-001: bolt.new Specification Probe

## Task
Execute an unassisted rapid AI prototyping probe using `bolt.new` to stress-test the functional boundaries of `context/FEATURES.md` (commit `0d0f20c`). Surface unstated architectural and behavioral assumptions before engineering begins.

## Tool and Model
- **Platform:** bolt.new (WebContainer-based full-stack agent)
- **Model:** Claude 3.5 Sonnet (via bolt.new engine)
- **Execution Mode:** Zero-shot single prompt. No interactive steering, iterative repairs, or follow-up prompt nudges.

## Economic Rationale
Manually identifying implicit ambiguities in specification edge cases requires hours of multi-role team debate. Running an autonomous full-stack generation cycle in under 3 minutes immediately exposes where an agent or implementer is forced to make assumptions due to underspecified criteria.

## Trust Boundary
- **Code Exclusion:** Absolute boundary. Zero code, templates, or configuration files generated by bolt.new may enter this repository.
- **Specification Impact:** bolt.new output is treated solely as untrusted diagnostic data. Behavioral assumptions are evaluated and converted into explicit EARS requirements or scope exclusions in `FEATURES.md`.

## Verification Performed
1. Inspect the live prototype generated in bolt.new against the acceptance criteria defined in `context/FEATURES.md`.
2. Inspect browser storage mechanisms via Chrome Developer Tools, confirming client-side mock database behavior.
3. Test input validation and negative pathways by submitting blank fields and malformed artifact links.
4. Identify all synthesized features absent from the specification (e.g., conditional scoring, record deletion, marketing routes).

## Findings
bolt.new made 5 major assumptions due to specification gaps:
1. Implemented a tri-state qualification tier (`Conditionally Eligible`) instead of binary evaluation.
2. Built a multi-page marketing route with informational landing cards.
3. Used a proprietary managed cloud database instead of Cloudflare D1 edge persistence.
4. Added candidate record deletion and status mutation controls for recruiters.
5. Ingested extra demographic attributes like institution and contact phone numbers.

All 5 assumptions have been resolved into explicit EARS boundary clauses or recorded under `## Exclusions` in `context/FEATURES.md`.
